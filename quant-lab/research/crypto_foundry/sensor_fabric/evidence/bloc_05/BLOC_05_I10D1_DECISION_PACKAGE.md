# 1 — Q1: PROVIDER-SIDE CONFIG OWNERSHIP

## 1.1 Operator ruling being tested

> I09-b retains ownership of provider semantic certification. I10 may own a narrowly
> scoped trade-side mapping adapter but cannot certify provider definitions by itself.

## 1.2 Does the frozen plan require the adapter to live in
`config/crypto_sensor_fabric/provider_semantics/`?

**No.** The frozen documents place *provider field semantics* in that directory, not the
mapping algorithm:

- `bloc_05/03` §12 — "**Planned config**: `provider_semantics/{kraken,gate,binance,bybit,
  okx,deribit,coinalyze,bitfinex_archive}.yaml`", each recording source endpoint, field
  name, data type, native unit, economic definition, timestamp meaning, interval scope,
  direction/side convention, exact normalization formula, **evidence reference**,
  semantic confidence, last verified date. That is a *record of semantics*, and it is the
  artifact I09-b must author.
- `bloc_05/06` §18 — the planned implementation tree lists `provider_semantics/` under
  `config/crypto_sensor_fabric/`, alongside `normalization/sensors/` under `src/`. The two
  are separate entries in the same frozen tree: config holds semantics, `sensors/` holds
  normalizers.
- `bloc_05/04` §2.2 — "This mapping gets its own methodology ID **and fixture tests**.
  Do not duplicate this logic in research code." A location requirement on *code*, and an
  explicit prohibition on research-code duplication — not a config-location requirement.

**Determination:** the adapter may safely reside in an I10-owned code namespace
(`normalization/sensors/`). No config file may be created in D1 (directive §12), and none
is required for the adjudication.

## 1.4 Minimum architecture — one authority, no second registry

```text
                    (text, read by the caller; I09-owned registries parse text only)
   semantic_equivalence.yaml ──project_planning_mapping()──► ProviderSemanticMapping
   (Bloc 1, evidence BLOC2_PROBE_PENDING,            │        (03 §11/§12 shape,
    confidence forced AMBIGUOUS)                     │         confidence AMBIGUOUS)
                                                    ▼
   normalization/sensors/side_maps.py  ──resolve(provider, provider_field, family)
        (I10-owned pure algorithm)                 │
        isBuyerMaker → SELL/BUY                    ├─► MethodologyRef("AGGRESSOR_…_V1","1")
                                                    │     via registry/methodology_registry.py
                                                    ▼
                                        admits_critical_t1_use(confidence)
                                                    │  False while AMBIGUOUS
                                                    ▼
                                   I10 sensor record: provisional evidence slot
                                   canonical aggressor_side stays UNKNOWN (B1-T10)
```

Properties:

1. **No second registry.** I10 writes no YAML, mints no methodology id, and holds no
   confidence authority. Every semantic fact is read from the I09-owned registries.
2. **One algorithm, no fork.** `providers/binance/probe.py::aggressor_side_from_is_buyer_maker`
   (lines 60–73) already pins the frozen R01 direction, and its own docstring states
   "The transformation implementation belongs to Bloc 5 normalization; this function pins
   the PROVISIONAL direction so an inversion can never be re-introduced silently."
   Production normalization code **must not import** `crypto_sensor_fabric.providers` (the
   forbidden-import firewall in all six scope audits: I01:202, I02:121, I03:105, I05:170,
   I08:181, I09:240). Therefore I10 re-implements the one-line map in `side_maps.py` and
   adds a **pin-consistency test** asserting I10's adapter, the probe pin, the fixture
   contract and the config `transformation_method` all agree on both boolean values. The
   test imports both sides; production imports neither.
3. **Fail-closed on absence.** Unknown `(provider, provider_field, sensor_family)` →
   `resolve()` returns `None` / `require()` raises `UnknownProviderSemanticMapping`
   (06 §1 G9). I10 maps that to `aggressor_side = UNKNOWN`, never to a guess.

**No config file is created in D1.** The eventual `provider_semantics/binance.yaml` is an
I09-b deliverable and is *not* on I10's critical path: `project_planning_mapping()` already
projects the live Bloc 1 row into the frozen shape with the correct `AMBIGUOUS` confidence.

# 2 — Q2: PROVIDER-EVIDENCE ROUTE (provisional-scoped, evidence-first promotion)

## 2.1 Route selected

**Provisional-scoped implementation with evidence-first promotion** — adopted as the
proposed initial route, for the four reasons the readiness assessment states and which the
frozen text independently supports: 03 §13 makes `AMBIGUOUS` blocking for critical T1
fields; the Bloc 1 schema rule **B1-T10** ("a provider's maker/taker boolean is not trusted
until a provider fixture test proves the mapping; untrusted records preserve
`aggressor_side=UNKNOWN` rather than guess") seals the same position at the N0 contract;
07 F17 forbids price-direction inference; and no qualifying provider evidence exists yet
(§2.3).

## 2.2 Two-layer acceptance matrix

```text
LAYER 1 — BEHAVIORALLY_IMPLEMENTED
  meaning: the pure transformation exists, is deterministic, is fixture-tested and is
           wired fail-closed.  It proves arithmetic, not semantics.
  earnable at B5-I10:  YES (adapter + fixtures + pin-consistency + refusal paths)

LAYER 2 — PROVIDER_SEMANTICALLY_VERIFIED
  meaning: first-party (or qualifying) provider documentation or a provider payload that
           demonstrates the side assignment exists; evidence_reference is no longer the
           pending token; SemanticConfidence leaves AMBIGUOUS; the canonical field may
           carry a real side.
  earnable at B5-I10:  NO — I09-b is DEFERRED and I10 has no certification authority.
```

# 4 — Q4: INITIAL PROVIDER COVERAGE (Binance USD-M slice + neutral refusal)

## 4.1 Slice selected

**Binance USD-M only, plus provider-neutral unknown-side behavior.** Justification is
narrow and stated as such: 04 §2.2 names the `isBuyerMaker` rule, the upstream methodology
id exists and resolves (`AGGRESSOR_FROM_BUYER_MAKER_BINANCE_V1`, status PROVISIONAL), and
an operator-frozen fixture exists. **None of this certifies Binance** — §2.2/§2.3 above
keep layer 2 unearned.

## 4.2 The four contracts

**(a) Provider-neutral schema contract** — two reusable N0/T1 objects, no provider token
anywhere:
```text
TradeObservationInput            # I10-owned transport-neutral input record
  provider, venue, native_instrument, contract_instance_id?
  native_event_id?, native_sequence_id?
  price_native: Decimal, quantity_native: Decimal, quantity_unit_evidence
  quote_notional_native?
  event_at?, observed_at, ingested_at
  side_evidence: SideEvidence    # ADT, see below
  aggregation_type, source_trade_count?
  raw_projection_refs, acquisition_refs, evidence_blob_hashes, code_version, config_version

SideEvidence = PROVIDER_BOOLEAN_FIELD(field_name, value)      # structurally present
             | SIDE_FIELD_ABSENT                              # provider has no side field
             | SIDE_SEMANTICS_UNDECLARED                      # field exists, no mapping row
```
The N0 target shape is the existing `MechanicalTrade` (`schemas/trade.py`, 02 §4) — reused,
never re-declared.

**(b) Binance mapping contract** — `SideEvidence=PROVIDER_BOOLEAN_FIELD("isBuyerMaker", b)`
and `(provider=BINANCE_USDM, provider_field=isBuyerMaker, sensor_family=MECHANICAL_TRADE)`
resolvable in the I09 registry ⇒ `SELL if b else BUY`, cited
`AGGRESSOR_FROM_BUYER_MAKER_BINANCE_V1` v1, confidence read (never assigned), emitted only
into the provisional slot while `AMBIGUOUS`.

**(c) Unsupported-provider refusal behavior** — for the other seven frozen providers
(`PROVIDER_IDS`, eight-provider structural contract): `SIDE_FIELD_ABSENT` or
`SIDE_SEMANTICS_UNDECLARED` ⇒ `aggressor_side = UNKNOWN` + `SEMANTICS_UNVERIFIED`;
`resolve()` returning `None` raises nothing upstream but **never** falls back to price
direction (07 F17) or to another provider's rule. A caller that *requires* a certified side
gets a typed `UnsupportedSideMappingError` (strict mode), so refusal is explicit rather
than silent.

**(d) Extension contract for subsequent providers** — adding provider X requires exactly:
(1) I09-b's `provider_semantics/x.yaml` row (semantics + evidence), (2) one entry in the
I10 mapping table keyed by `(provider, field, family)`, (3) a deterministic fixture with a
`provenance` field (06 §5/§20), (4) a methodology row only if the transform is new. The
common normalizer changes by **zero lines** — it consumes `SideEvidence` and the registry,
never a provider token.

**Eight-provider program scope is preserved.** This first slice is an implementation
order, not a coverage reduction: 06 §5's required provider set (Kraken, Gate, Binance
USD-M, Bybit, OKX, Deribit, Coinalyze, Bitfinex community archive) is untouched.
