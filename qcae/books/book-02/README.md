# QCAE Book II — Discovery & Repository Intelligence

**Canon:** QCAE v0.1  
**Status:** IN BUILD  

Book II answers two questions:

1. Given a frozen capability contract and atom model, how does QCAE discover the strongest plausible implementations without becoming repository/popularity biased?
2. Once a candidate is found, how does QCAE understand what actually exists inside the source before the Proving Lab spends expensive verification budget?

## Blocks

### Block 2 — Discovery Intelligence
Transforms capability contracts and atoms into diversified discovery plans, searches internal/external surfaces, deduplicates candidates, preserves source provenance, and ranks candidates for deeper investigation.

### Block 3 — Repository Intelligence / DeepWiki Layer
Builds a source-grounded structural understanding of candidate repositories. DeepWiki is an explanation/comprehension accelerator; repository source remains authoritative.

### Block 4 — Capability Forensics
Recovers the minimum extractable unit, interfaces, specifications, hidden assumptions, complexity, and alternative implementations required for acquisition decisions.

## Book II laws inherited from Book I

- Search begins from capability semantics, not product names.
- Repository is a source container, not the durable unit of capability identity.
- Discovery can propose contract amendments but cannot silently rewrite a contract.
- Claimed relationships remain distinct from source/runtime/contract verification.
- Internal capability must be searched before creating unnecessary external acquisition burden.
- Discovery should maximize useful coverage and diversity, not raw result count.
- DeepWiki/LLM explanations are analysis, never proof.
- Negative discovery and prior rejection knowledge remain reusable.
- Expensive forensic/proving work should be allocated only after cheaper evidence has reduced the candidate space.

## Commit discipline

Every chapter receives its own commit. Each block ends with an integration/freeze review. Amendments remain separate commits so future build agents can trace assumptions and regressions to narrow historical checkpoints.
