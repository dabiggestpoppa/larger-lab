# 0. Purpose

This review asks whether the Foundry has enough constitutional, resource, data, refinery, and evaluation design to generate the **first bounded implementation prompt** without prematurely authorizing model training.

The intended first implementation is infrastructure only:

- schemas/contracts;
- registries;
- local deterministic tooling;
- provider observation/normalization;
- data provenance/rights/partitioning;
- dataset manifests;
- evaluation harness;
- sealed-eval access structure;
- receipts/tests.

It does **not** authorize:

- continued pretraining;
- SFT;
- preference/RL training;
- material paid GPU campaigns;
- CEREBUS reveal/rediscovery experiments;
- OCE runtime promotion.

# 3. Integration findings

## INT-01 — Temporary registries could duplicate OCE

**Resolution:** first implementation uses Foundry-local domain registries only for model/data/experiment semantics. Generic identity/authority/evidence/workflow abstractions remain explicit adapters/test doubles with replacement markers.

**Gate condition:** every generic-looking local fixture includes `canonical_oce_target` + `replacement_condition`.

**Status:** CLOSED BY PROMPT REQUIREMENT.

---

## INT-02 — Resource router can run before Resource Intelligence exists

**Resolution:** B1 implementation may build read-only provider adapters, offer normalization, cost receipts, and a local placement simulator. It may not create production provider credentials/authority or unattended autonomous rental.

**Status:** CLOSED.

---

## INT-03 — Rights evaluation cannot be fully automated

**Resolution:** registry can encode rights evidence/disposition, but UNKNOWN / review-required remains operator/human hold rather than model inference.

**Status:** CLOSED.

---

## INT-04 — Dataset refinery may accidentally consume unratified sources

**Resolution:** DatasetManifest builder accepts only SourceRecords whose role and rights state satisfy frozen B2 policy.

**Status:** CLOSED.

---

## INT-05 — Evaluation harness could expose sealed payloads during development

**Resolution:** initial implementation must support physically/logically separate sealed payload path and evaluator-only interface. Tests prove builder-facing APIs cannot enumerate answer keys.

**Status:** CLOSED BY BUILD GATE.

---

## INT-06 — Benchmark authoring itself can create contamination

**Resolution:** BenchmarkSpec records author/model lineage before benchmark activation. Evaluation artifacts generated by models exposed to target answers are not assumed independent.

**Status:** CLOSED.

---

## INT-07 — Reproducibility levels could become labels without tests

**Resolution:** no run receives a reproducibility class merely by declaration. The first implementation supports evidence fields; later drills produce the actual class.

**Status:** CLOSED.

---

## INT-08 — Cost optimization can become premature autonomous spending

**Resolution:** first implementation is `OBSERVE / NORMALIZE / SIMULATE`. Actual paid resource launch remains operator-triggered and separately authorized.

**Status:** CLOSED.

---

## INT-09 — Data-quality vector can become another arbitrary scoring engine

**Resolution:** v0 stores dimensions and policy reasons; it does not derive one universal quality number.

**Status:** CLOSED.

---

## INT-10 — Foundry may overbuild before first useful experiment

**Resolution:** first implementation follows minimum viable scientific substrate. No UI, multi-tenant system, generic cloud manager, broad agent framework, or distributed scheduler is required.

**Status:** CLOSED.

# 7. Required proof scenarios

Before the first implementation gate can PASS, test at least:

1. unknown-rights source cannot enter TRAIN;
2. retrieval-only source cannot be packed into training dataset;
3. eval solution duplicate/paraphrase creates contamination relation;
4. CEREBUS-family source is blocked from blind-discovery train partition;
5. synthetic child retains generator ancestry;
6. two provider offers normalize into one ComputeRequest comparison;
7. cheapest hourly offer can lose cost-to-close simulation;
8. resource layer cannot autonomously rent GPU;
9. changed dataset transformation creates new fingerprint/version;
10. related time-series rows cannot leak through naive random split policy;
11. evaluation protocol cannot mutate after freeze;
12. builder interface cannot read sealed answer payload;
13. same artifact under different runtime produces distinct evaluation subject identity;
14. tool-augmented system result cannot be credited as artifact-only result;
15. benchmark exposure can downgrade lifecycle status;
16. unknown/failed run can become NegativeKnowledge with reopen conditions;
17. temporary OCE fixture declares replacement target and cannot claim canonical authority.

# 9. Prompt-readiness decision

No unresolved architecture contradiction prevents the **MF-B0→MF-B4 infrastructure build prompt**.

The plans now define:

- what the Foundry is and is not;
- what compute can do;
- how data earns a role;
- how data becomes a reproducible corpus;
- how evaluation remains independent from training;
- how current OCE services are consumed rather than duplicated;
- what must remain deferred until evidence exists.

**Gate:** `READY_FOR_MF_B0_B4_MASTER_BUILD_PROMPT`

This is readiness for a **bounded infrastructure implementation prompt**, not readiness to train the specialist model.

After implementation and evidence review, the next planning sequence is:

`MF-B5 Base Model Tournament -> MF-B6 Specialist Adaptation -> MF-B7 Tool/Coding Competence`, while MF-B8/B9/B10 remain separately gated.
